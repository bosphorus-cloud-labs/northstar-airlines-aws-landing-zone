# Enterprise landing-zone Terraform reference

Status: reference implementation only. Nothing in this directory is deployed, and it is isolated from the existing application and simulation states.

## Ownership and deployment order

1. Establish AWS Organizations and an AWS Control Tower landing zone through supported AWS procedures. Confirm the management, Audit, and Log Archive accounts, home Region, registered OUs, IAM Identity Center, Account Factory portfolio, quotas, and service-linked roles.
2. Create a dedicated AFT Management account and an encrypted, versioned bootstrap backend independently. Run bootstrap with credentials already authenticated to the Control Tower Management account; the official module assumes `AWSControlTowerExecution` into AFT Management, Audit, and Log Archive. Do not use application state.
3. Let AFT create/connect the four source repositories. Populate each from the templates generated by the deployed AFT 1.23.0 module, then overlay the examples here after comparing upstream changes. Submit account requests only after the global and named account customization repositories exist.
4. Operate Organizations SCPs from a distinct management-account state and identity. Operate network core from a network-account state; operate workload attachments from per-account states. Never allow two states to own the same resource or policy attachment.

The AFT bootstrap provider verifies that its caller is in the Control Tower Management account. The caller requires the official AFT bootstrap permissions, including administrative Control Tower/Service Catalog access and permission to assume the existing `AWSControlTowerExecution` roles in AFT Management, Audit, and Log Archive. The trust relationships and roles must exist before bootstrap. The example does not create an Organization, landing zone, core accounts, source repositories, execution roles, or backend.

## Directory map

| Path | Implemented reference |
| --- | --- |
| `aft-bootstrap/` | Pinned official AFT module, four-account inputs, checks, provider and backend examples |
| `account-requests/` | AFT repository layout and Production workload request |
| `global-customizations/` | Account password policy and S3 account public-access block for every AFT-managed account |
| `account-customizations/` | Distinct Production and Development budget controls |
| `organizations/` | Customer-managed SCP resources and explicit OU attachments with deletion protection |
| `networking/` | Central TGW/RAM/VPN/GWLB core and separate workload attachment root |
| `ci/` | Inactive plan/apply workflow examples and recovery guidance |
| `tests/` | Offline policy, targeting, ownership, isolation, and environment-difference checks |

SCPs restrict the maximum available permissions; they never grant IAM permissions. The Organizations root owns only policies named `northstar-*` and their explicit attachments. It must not import or manage Control Tower-owned policies or attachments. `prevent_destroy` is a guardrail, not a substitute for review: intentional retirement requires a separately approved code change and attachment impact assessment.

The regional SCP exempts only global control-plane actions; KMS and AWS Config remain region-restricted. `AWSControlTowerExecution` and a pre-created `NorthStarEmergencyRepair` role are excluded from the regional and security-service denies so authorized landing-zone repair is possible. These exclusions do not grant permissions: IAM, trust policy, MFA, session duration, monitoring, and approval controls must independently restrict both roles. Validate effective policies and rehearse emergency access before attachment.

## Fleet governance lifecycle

New accounts enter through an account request, Control Tower vending/enrollment, account provisioning customizations, global customization, then the selected account customization. Existing Control Tower accounts require the AWS-supported AFT import/update request flow; adding an account to Terraform state or writing directly to AFT tables is not enrollment. Immutable Control Tower request fields such as account email/name cannot be repurposed after vending.

Global baseline changes are rolled out through AFT customization pipelines. Start with Development/canary accounts, inspect plan-only results where supported, then use bounded environment waves. Environment SCP changes use the central Organizations root: plan attachment changes, validate effective policies, then promote one OU at a time. SCP and AFT states remain independent.

AFT records executions and supports retry, but safe retry depends on idempotent Terraform and helper scripts. For a failed customization, retain the trace token and logs, classify transient versus configuration failure, correct forward, and rerun the affected account customization. Do not manually create a resource that Terraform owns. Drift detection is proposed through scheduled read-only plans/AFT plan-only invocations and AWS Config; no scheduler is implemented here.

Control Tower supplies its managed Config and logging baseline. Security Hub delegated administration, Config aggregation, finding normalization, and event delivery to the NorthStar dashboard remain proposed integrations. A production collector would authenticate in dedicated security accounts, retain source account/Region/control/revision/timestamps, and publish through a new reviewed ingestion boundary. The current dashboard remains synthetic and read-only; these examples do not make it a real fleet collector.

## Offline validation

Run from the repository root:

```sh
terraform fmt -check -recursive terraform/enterprise
python3 terraform/enterprise/tests/test_enterprise.py
terraform -chdir=terraform/enterprise/aft-bootstrap init -backend=false -input=false
terraform -chdir=terraform/enterprise/aft-bootstrap validate
terraform -chdir=terraform/enterprise/organizations init -backend=false -input=false
terraform -chdir=terraform/enterprise/organizations validate
terraform -chdir=terraform/enterprise/networking/core init -backend=false -input=false
terraform -chdir=terraform/enterprise/networking/core validate
terraform -chdir=terraform/enterprise/networking/workload-attachment init -backend=false -input=false
terraform -chdir=terraform/enterprise/networking/workload-attachment validate
terraform -chdir=terraform/enterprise/account-requests/terraform init -backend=false -input=false
terraform -chdir=terraform/enterprise/account-requests/terraform validate
terraform -chdir=terraform/enterprise/global-customizations/terraform init -backend=false -input=false
terraform -chdir=terraform/enterprise/global-customizations/terraform validate
terraform -chdir=terraform/enterprise/account-customizations/production/terraform init -backend=false -input=false
terraform -chdir=terraform/enterprise/account-customizations/production/terraform validate
terraform -chdir=terraform/enterprise/account-customizations/development/terraform init -backend=false -input=false
terraform -chdir=terraform/enterprise/account-customizations/development/terraform validate
```

The enterprise tests render every AFT provider/backend template with representative OSS values and run Terraform formatting checks. Release verification also initializes and validates temporary rendered copies; direct validation of the source directories checks their ordinary `.tf` files but ignores `.jinja`. Provider installation requires registry access. Validation proves configuration/schema consistency only; it does not prove permissions, prerequisites, reachability, quotas, Control Tower health, route symmetry, appliance health, or deployment.
